# 从 0 到 100%：一个专用验证码识别模型的训练记录

这份文档记录了为 J-PlatPat（日本特许厅专利检索平台）的图片验证码，从收集数据、标注、训练、评估到部署进浏览器插件的完整过程。
里面的数字都来自实际运行，失败和踩过的坑也写在里面。

---

## 1. 问题

在 J-PlatPat 下载公报 PDF 时，访问稍频繁就会弹出图片验证码：

- **固定 4 位纯数字**，300×60 的 GIF
- 灰色渐变背景，一两条横穿的干扰线，数字有轻微抖动和重影
- 四周有 1 像素黑框

现成的通用模型可以直接用，但准确率不够：

| 模型 | 在我们的数据上（人工确认的难例） |
|---|---|
| [ddddocr](https://github.com/sml2h3/ddddocr) 1.6.1 | 93.6% |
| [ppllocr](https://github.com/gitpetyr/ppllocr) 2.2 | 86.3% |

ddddocr 的错误很有规律：
- **漏掉相邻的重复数字**：`0112` → `012`，`7145` → `745`
- **把开头的干扰线认成 7**：`3524` → `73524`

这两类错误都是"不定长识别（CTC 类）"的典型问题。而这个验证码**永远是 4 位**，正适合用"定长分类"来做。


## 3. 数据收集

### 3.1 先摸清页面行为

收集插件的关键是**自动判断标签**。在真实页面上挂了一个记录器，测出三种情况：

| 操作 | 页面表现 |
|---|---|
| 点「再描画」/ 空提交 | 图片元素先**消失约 0.8 秒**，再出现新图 |
| 输错 | 同上，换新图，**没有任何错误提示** |
| 输对 | 同一张图闪回约 0.2 秒，然后**对话框关闭** |

于是标签可以自动得到：
- 提交后对话框关闭 → `ok/`，你输入的值就是**正确答案**
- 提交后换了新图 → `wrong/`，你输入的值是错的
- 没提交就换图 → `unlabeled/`

> **踩坑**：最初的版本把"图片消失"当成"对话框关闭"。但输错时图片也会先消失 0.8 秒，导致**输错的图被标成了正确答案**。改成"整个对话框消失才算通过"后解决。这种标签污染在训练阶段很难被发现，必须在源头避免。

### 3.2 自动换图

正常使用时每次下载只出一张验证码，攒数据太慢。插件加了"自动换图"：对话框打开后，定时点「再描画」，每出一张新图就存一张。
- 间隔 1～1.5 秒随机，并且**等新图真正出来再计时**（新图大约 0.8 秒出来，固定间隔会把正常加载误判成"卡住"）
- 连续 3 次换图失败 → 判断为被限流，自动停止
- 多个窗口同时收集时，由后台统一计数，避免各页面互相覆盖进度

### 3.3 一个意外发现：验证码来自固定图库

随着数据增多，**完全相同的图片**越来越多。如果图片是从大小为 P 的图库里有放回地随机抽取，抽 N 张时不重复的期望张数是 `U = P·(1 − e^(−N/P))`，反解就能估出 P：

| 轮次 | 收集 | 不重复 | 估计图库大小 |
|---|---|---|---|
| 第一轮 | 373 | 369 | ≈ 17,300 |
| 第二轮 | 2,070 | 1,940 | ≈ 15,800 |
| 第三轮 | 3,410 | 3,031 | ≈ 14,200 |

三次独立估计都在 **1.4 万～1.7 万张**之间，可以判断 J-PlatPat 的验证码不是实时生成的，而是从一个约 1.5 万张的**固定图库**里随机抽取。

两个后果：
1. **训练前必须按像素去重**，否则同一张图可能同时出现在训练集和测试集，准确率会虚高。
2. 继续收集的边际收益递减：收得越多，重复越多。

## 4. 标注：让模型帮人标

标注工具是一个本地网页（`label_server.py`，只用 Python 标准库），双击 `start_label.bat` 打开。

核心思路是**多模型交叉预标注**：
- 同时跑 ddddocr、ppllocr 和自己训练的模型，结果并排显示，点一下就能采用
- **两个原理不同的模型结果一致** → 直接批量采用
- 不一致的才需要人看（筛选"只看可疑"）

这个策略是否可靠，要用数据说话。第二轮用交叉验证（见 §6）检验：

> 在人工确认过的图上，ddddocr 和 jpp_cnn **一致的 552 张里，552 张全部正确（100%）**。

所以第三轮 3,410 张里，人工只看了 609 张，其余 2,801 张全是两模型一致后自动采用的。

### 标注工具的几个细节

- 已标注、未标注、自动采用、跳过用不同的边框和标签区分，一眼就能看出来
- 左右两栏各自滚动，审核区固定在左上
- 模型文件更新后（重新训练），旧的预测**自动作废**。这是靠记录"预测时用的模型文件修改时间"来判断的
- "准确率"只拿人工确认的图对照计算。因为 jpp_cnn 就是用这些图训练的，所以界面上专门提示：它在已标注图上的准确率会偏高，真实水平要看交叉验证

## 5. 模型

### 5.1 为什么是"定长多头分类"，不是 CTC

| 方案 | 适合 | 本项目 |
|---|---|---|
| CRNN + CTC | 位数不定 | 会出现漏字、多字（ddddocr 的错误正是这类） |
| **CNN + 4 个分类头** | **位数固定** | 每一位固定是 0～9 的十选一，结构上不可能漏字、多字 |

### 5.2 网络结构（0.96M 参数）

```
输入 1×48×240（灰度，原图裁掉 1px 黑框后等比缩放）
4 × [Conv3×3 → BN → ReLU → Conv3×3 → BN → ReLU → MaxPool2]   通道 32 → 64 → 96 → 128
→ 128×3×15 → 按行平均 → 128×15 → Dropout → FC 1920→256 → ReLU → Dropout → FC 256→40
→ reshape 成 4×10，每一位做 softmax
损失：4 个交叉熵之和（label smoothing 0.05）
```

### 5.3 数据增强（全部在 GPU 上，用 `affine_grid` 实现，不依赖 torchvision）

- 旋转 ±4°，缩放 ±6%，水平和垂直平移各 ±8%
- 对比度 ±20%，亮度 ±10%，随机高斯噪声
- **不做水平翻转**（数字翻过来就不是原来的数字了）

> **踩坑**：原图四周有 1 像素黑框。旋转或平移时，`padding_mode='border'` 会把黑框拉伸成边缘的**黑色楔形**，而真实验证码里没有这种东西。解决办法是预处理先裁掉 1 像素再缩放。这个参数（`crop: 1`）写进模型说明文件，训练、标注工具、插件三处共用，保证一致。

### 5.4 训练设置

- AdamW，lr 2e-3，weight decay 1e-3，OneCycle 学习率
- **取最后一轮的权重**，不按验证集挑"最佳轮次"。验证集很小时，挑最佳轮次本身就是一种过拟合
- 训练轮数随数据量自动调整，总步数保持在约 3000 步：369 张时 200 轮，3,031 张时 63 轮
- RTX 3060 Laptop：一次训练约 1～3 分钟

### 5.5 置信度为什么只有 0.8～0.9

用了 label smoothing 0.05 后，每一位的最大概率大约在 0.95 左右，4 位相乘 ≈ 0.83。所以**模型完全认对时，整串置信度也通常只有 0.8～0.9**，这是正常的。插件里"没把握就换一张"的门槛设成 0.7，而不是 0.9 或 0.99。

## 6. 评估：怎样才算"公平"

### 6.1 三个容易犯的错

1. **在训练数据上测准确率**：模型见过这些图，必然虚高。
2. **验证集太小**：55 张里错 1 张就差 1.8 个百分点，数字主要反映运气。
3. **在"自动采用"的图上比较模型**：这些图本来就是 ddddocr 和 jpp_cnn 结果一致才被采用的，两个模型在上面都"天然全对"。

### 6.2 做法

- **5 折交叉验证**：每张图都由"没见过它"的模型来预测（`cross_validate.bat`）
- 公平对比**只看人工确认的图**。这些图里很多正是两个模型意见不一的难例
- 交叉验证的预测结果写成只读模型 `jpp_cnn_cv`，可以在标注工具里逐张复查

### 6.3 结果

| 轮次 | 去重后样本 | 其中人工确认 | jpp_cnn（交叉验证） | ddddocr | ppllocr |
|---|---|---|---|---|---|
| 第一轮 | 369 | 369 | **98.6%**（错 5 张） | 96.7% | — |
| 第二轮 | 1,940 | 530 | **100%**（0 错） | 93.6% | 87.2% |
| 第三轮 | 3,031 | 590 | **100%**（0 错） | 93.6% | 86.3% |

第三轮逐张对照（人工确认的 590 张）：

| | 张数 |
|---|---|
| 两个都对 | 552 |
| **只有 jpp_cnn 对** | **38** |
| 只有 ddddocr 对 | 0 |
| 两个都错 | 0 |

置信度门槛（第三轮交叉验证，全部 3,031 张）：

| 置信度 ≥ | 覆盖 | 其中准确率 |
|---|---|---|
| 0.5 | 100.0% | 100% |
| 0.7 | 100.0% | 100% |
| 0.8 | 99.6% | 100% |
| 0.9 | 5.0% | 100% |

第一轮认错的 5 张，置信度全部低于 0.45，而认对的普遍在 0.8 以上。**置信度能很好地区分"有把握"和"没把握"**，这就是插件里"低置信就换一张"的依据。

### 6.4 "100%"的正确理解

- 3,031 张 0 错，按"三法则"（rule of three）估算，真实错误率 95% 置信上限约为 3/3031 ≈ **0.1%**。
- 局限：自动采用的标签来自模型一致，可能存在"模型和标签一起错"的情况，交叉验证查不出来。最终的检验是**实际使用**：提交后 J-PlatPat 判对还是判错。插件会统计这个实测准确率。

## 7. 部署：在浏览器里跑模型

### 7.1 为什么不用 onnxruntime-web

onnxruntime-web 的 WebAssembly 文件有十几 MB，而且在 Chrome 插件（Manifest V3）里还要处理内容安全策略等限制。模型只有 0.96M 参数，**直接用纯 JavaScript 实现前向计算**更简单：
- `export_web.py` 把 BatchNorm 折进卷积权重（`w·γ/σ`，`b = β − μ·γ/σ`），导出成一个 3.9MB 的 float32 文件和一份描述层结构的 JSON
- `extension/model.js` 大约 250 行，没有任何第三方依赖

### 7.2 预处理必须逐像素一致

训练用的是 PIL，浏览器里没有 PIL，所以在 JS 里**复刻了 PIL 的算法**：
- 灰度：`L = (R·19595 + G·38470 + B·7471 + 0x8000) >> 16`
- 缩放：照抄 Pillow `Resample.c` 的 BILINEAR 实现。注意它不是简单的双线性插值：缩小时滤波器的支撑范围会随缩放比放大，系数用 22 位定点数，先水平后垂直，中间结果取整成 8 位

### 7.3 验证

用 809 张真实验证码（全部 609 张人工确认的难例 + 200 张随机）对比 JS 和 PyTorch：

| 检查项 | 结果 |
|---|---|
| 预处理后的像素 | 20 张逐像素比对**完全相同**（最大差 0），809 张像素总和全部吻合 |
| 预测结果 | **809 / 809 与 PyTorch 相同** |
| 置信度 | 最大差 4.8 × 10⁻⁷（浮点误差） |

### 7.4 性能

| 版本 | 每张耗时 |
|---|---|
| 朴素实现（每个卷积核扫 9 遍特征图） | 1,135 ms |
| 补边 + 单遍扫描 + 一次算 4 个输出通道 | **中位数 174 ms，P95 246 ms** |

### 7.5 插件行为

- 验证码出现 → 本地识别 → 填进输入框，旁边显示"识别结果 · 置信度 · 耗时"
- 置信度低于 0.7 → 自动换一张，每个对话框最多 3 次。仍然没把握时照样填入，并用红字提醒核对
- 你已经自己输入的不会被覆盖；上一张刚被判错时，用新识别结果覆盖旧答案
- 自动提交，判错就重新识别再提交（每个对话框最多 3 次）。只有对话框出现前 15 秒内有真实的用户操作（`isTrusted` 事件）才会自动提交，由脚本触发的只填入不提交。操作可以在本页，也可以是打开本页之前的那一次（从列表点开文献到新标签页、刷新），后者靠 `chrome.storage.local` 在页面间共享（v0.3.2）
- 统计"用模型的答案提交后，被 J-PlatPat 判对 / 判错"的次数，得到实测准确率
- 自动点「文献単位PDF」的确认框里的「継続」；验证码通过后自动点「PDFダウンロード」，并拦下 J-PlatPat 的 PDF 查看器窗口（`window.open('/p0205')`），改为直接下载 `localStorage.p0205Param` 里列出的 PDF

## 8. 踩过的坑（环境篇）

| 问题 | 原因 | 解决 |
|---|---|---|
| ddddocr 识别结果全是空字符串 | 1.6.1 的 `set_ranges(0)` 有 bug | 改用 `set_ranges('0123456789')` |
| 装 onnx 后 ddddocr 无法导入 | onnx 把 numpy 升到 2.x，而 OpenCV 4.8 是按 numpy 1.x 编译的 | 退回 `numpy==1.26.4`，onnx 用 1.18 |
| 装 ppllocr 又要升级 numpy | 它依赖新版 opencv-python-headless | `pip install --no-deps ppllocr`（numpy、OpenCV、onnxruntime 已经满足） |
| 标注工具找不到数据目录 | Windows 的"下载"文件夹被移到了别的盘 | 从注册表和 Chrome 设置里读取实际下载目录 |
| 多窗口收集时进度乱跳 | 每个页面各自读-改-写同一个计数 | 由后台统一发号，storage 写入排队 |

**教训**：装任何包之前先 `pip install --dry-run`，确认它不会动 numpy 这类基础库。

## 9. 复现

```bash
# 1. 收集：Chrome 加载 extension/，在 J-PlatPat 正常使用或用"自动换图"
# 2. 标注：双击 start_label.bat（或 python label_server.py）
# 3. 训练：双击 train.bat（或 python train.py）→ models/ 和 extension/model/ 同时更新
# 4. 评估：双击 cross_validate.bat（或 python train.py --cv 5）→ models/jpp_cnn_cv_report.txt
# 5. 到 chrome://extensions 重新加载插件
```

依赖：Python 3.11，PyTorch 2.x（有 CUDA 更快），numpy 1.26，Pillow，onnx 1.18，onnxruntime；可选 ddddocr、ppllocr。
